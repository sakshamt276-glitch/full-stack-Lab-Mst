Experiment Notes

Concurrency: every order ticks independently in a single global loop; only one is "focused" for the inspector, map, and detail panels at a time — placing or tracking an order changes focus without pausing the rest.

Pattern: client polls (or receives simulated WebSocket pushes) for order state instead of the server holding an open connection per request.

Envelope contract: every response follows {success, data/message, correlationId, timestamp} so the client parses one shape regardless of endpoint.

Resilience: when the backend goes down, requests fail and the client retries with exponential backoff (2s → 4s → 8s → capped at 16s).

Persistence: all orders and which one is focused are written to localStorage on every change, so a refresh restores state — standing in for a real database.

Tradeoff demoed live: in Polling mode every tick on the focused order is logged; in WebSocket mode only state-change events are logged.

Architecture

Browser → GET /api/orders/{id}/status (or WS push) →
Order Service (mock, in-memory state machine, handles N concurrent orders) →
State Store (localStorage stands in for Postgres/Redis)

Responses use a standardized envelope with a correlation ID for request tracing. On failure, the client retries with exponential backoff.
